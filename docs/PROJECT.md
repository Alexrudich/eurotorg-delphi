# Как устроен «Складской учёт»

README отвечает на «как запустить». Этот файл — на «как устроено и почему
сделано именно так».

---

## 1. Решения и их причины

### 1.1. Один DataModule на весь доступ к данным

Всё, что касается базы, живёт в `Source/Data/uDM.pas` (~1350 строк):
соединение, запросы, транзакции. Файл разбит на последовательные секции —
соединение → справочники → документы → отчёты — и читается сверху вниз.

Слои «UI / сервисы / репозитории» здесь не делались сознательно: у одного
десктопного приложения с одним окном они не дают ничего, кроме 25 файлов
вместо трёх. При этом граница между UI и данными соблюдена: форма не пишет
SQL, все запросы — в TDM. Если приложение когда-нибудь дорастёт до слоёв,
TDM почти дословно станет сервисом и репозиторием.

### 1.2. UI целиком создаётся кодом, MainForm.fmx — пустой каркас

`Source/Forms/MainForm.pas` (~2640 строк) строит все вкладки, гриды и поля
в коде (`Create*Controls` / `Create*Columns`).

- макет правится как обычный код: изменения видно в diff, не нужен RAD Studio,
  чтобы понять, что где лежит;
- нет рассинхрона `.fmx` и `.pas` — частого источника конфликтов;
- три вкладки-справочника почти одинаковые — логика параметризована, а не
  скопирована в дизайнере трижды.

### 1.3. Остаток — производная от журнала движений

`StockMovement` — единственная правда: приход `+`, расход `−`, перемещение
`−` со старого места и `+` на новое. Остаток партии = `SUM(Quantity)` по
журналу до нужного момента. Отчёт `usp_StockOnDate` считает именно так,
поэтому «остатки на любую дату/время» работают бесплатно и не могут
разойтись с реальностью.

### 1.4. `Batch.Quantity` — кэш, а не источник правды

Поле дублирует сумму движений и нужно для двух быстрых операций: FIFO-подбор
и проверка «не уйти в минус». Инвариант `Batch.Quantity =
SUM(StockMovement.Quantity)` проверяется автоматически: самопроверками в
`02_seed.sql` и `03_perf_seed.sql` (на 980 тыс. движений расхождений — 0)
и smoke-тестом (проверка B.6).

### 1.5. Расход только после подтверждения

Перед записью расхода `PeekOutcomeFIFO` / `PeekOutcomeManual` считают, какие
партии уйдут (FIFO: по `IncomeDate`, при равенстве — по `BatchId`, чтобы
порядок был детерминированным), и показывают список в диалоге. Ошибка «не
хватает 8 шт» возникает до открытия транзакции — полузаписанных документов
не бывает.

### 1.6. Один курсор на соединение (без MARS)

ODBC-соединение FireDAC по умолчанию не поддерживает несколько активных
результатов. Перед любой записью (`DocumentIncome`, `DoOutcome`,
`DocumentTransfer`) `SaveAndCloseDictCursors` закрывает курсоры справочников,
после — `RestoreDictCursors` открывает их заново с восстановленной позицией.
Это же — причина однопользовательского режима (раздел 6).

### 1.7. Перемещение = расщепление партии

Перемещение части партии создаёт на новом месте новую партию с сохранением
`IncomeDate` и `ExpiryDate` — FIFO-возраст и срок годности «едут» вместе с
товаром. Старая партия уменьшается на перемещённое количество.

### 1.8. Поиск и сортировка: белый список и экранирование

- `SafeSort` принимает сортировку только из белого списка колонок — SQL-инъекция
  через заголовок грида невозможна физически;
- `LikePattern` экранирует `%`, `_`, `[` в строке поиска — «100%» ищется как
  текст, а не как маска;
- debounce-таймер 350 мс — поиск не дёргает базу на каждое нажатие клавиши.

### 1.9. Нагрузочные данные — в отдельной базе

`Sql/03_perf_seed.sql` создаёт `WarehousePerfTest` (копия схемы, 5000 товаров,
700k партий, ~980k движений, ~1 ГБ). Рабочая `WarehouseDB` не трогается,
очистка — одна команда `DROP DATABASE` в конце файла. Объём задаётся
параметром: `-v BATCHES=700000` (по умолчанию 70k).

### 1.10. SQL-скрипты — в UTF-8 с BOM

`sqlcmd` определяет кодировку файла по BOM; без него читает скрипт в кодовой
странице консоли и кириллица в базу попадает искажённой. Все `.sql` сохранены
с UTF-8 BOM — при редактировании его нужно сохранять.

## 3. Замеры производительности

Контекст: MS SQL Express 2025 (локально, Shared memory), база
`WarehousePerfTest`: 5000 товаров, 700 000 партий, ~980 000 движений, ~1 ГБ.
Скрипт: `sqlcmd -S localhost\SQLEXPRESS -E -C -i Sql\04_perf_measure.sql`.

| Операция | Время | Комментарий |
|---|---|---|
| `usp_StockOnDate` на один товар | 9–140 мс | обычный сценарий оператора |
| FIFO-подбор 1000 шт | ~80 мс | запрос подбора партий по товару |
| Поиск `LIKE N'Товар_%'` по 5000 товаров | ~3 мс | с префиксной маской |
| `usp_StockOnDate` без фильтра (вся база) | 27–30 с | ~700 000 строк выдачи |

Выводы:

- узкое место полного отчёта — не вычисление, а **объём выдачи** (700k строк
  через ODBC). На одном товаре тот же отчёт занимает десятки миллисекунд,
  поэтому при необходимости лечится фильтром `WHERE b.GoodsId = @GoodsId`
  в процедуре;
- покрывающий индекс `IX_Mov_Date_Covering (MovementDate) INCLUDE (BatchId,
  PlaceId, Quantity)` превращает скан журнала в покрытое чтение — на нём
  держатся и отчёт, и FIFO;
- замеры воспроизводимы: `03_perf_seed.sql` детерминированно пересоздаёт базу.

## 4. Как проверять

| Что | Команда | Ожидание |
|---|---|---|
| Окружение | `powershell -ExecutionPolicy Bypass -File setup_check.ps1` | exit 0; `[WARN]` по TCP/IP — норма для локального запуска (Shared memory), TCP нужен только для удалённого подключения |
| Схема + сид | `sqlcmd -S localhost\SQLEXPRESS -E -C -i Sql\01_schema.sql` затем `02_seed.sql` | самопроверки сида без ошибок |
| Smoke по SQL | `sqlcmd -S localhost\SQLEXPRESS -E -C -i Sql\00_smoke_test.sql` | результаты совпадают с ожиданиями в комментариях |
| Smoke из приложения | `build.cmd` (или собрать `smoke.dpr` и запустить `bin\smoke.exe`) | `SMOKE OK`, exit 0 |
| Нагрузочные замеры | `sqlcmd -S localhost\SQLEXPRESS -E -C -v BATCHES=700000 -i Sql\03_perf_seed.sql`, затем `04_perf_measure.sql` | см. раздел 3 |

Smoke-тест (`smoke.dpr`) — три сценария, 14 проверок:

- **A.** отчёт «остатки на дату» на сид-данных в пяти контрольных точках
  (включая границы: 23:59 накануне, момент перемещения, «до первого прихода»);
- **B.** полный жизненный цикл на временных данных: два прихода → Peek FIFO →
  FIFO-расход 120 шт через границы двух партий → сверка остатков и кэша
  `Batch.Quantity` с журналом → отказ при расходе сверх остатка; всё созданное
  удаляется в `finally` (база не меняется);
- **C.** поиск и сортировка справочника через тот же код, что использует UI
  (`OpenGoods` с фильтром и `SafeSort`).

## 5. Что здесь не делалось и чем заменено

- **Слои и DI.** Граница одна и соблюдается: форма не пишет SQL, весь он в
  TDM. Для одного приложения этого достаточно.
- **Юнит-тесты с моками.** Роль тестов выполняют интеграционные проверки
  (`smoke.dpr` + самопроверки в SQL-скриптах) против настоящей СУБД. Когда
  90% логики — это SQL, гонять его на моках бессмысленно.
- **Многопользовательская конкурентность.** Условие задания — одно рабочее
  место, поэтому вместо оптимистической блокировки (`RowVersion`) или
  `UPDLOCK/HOLDLOCK` в FIFO-подборе — обычные транзакции и последовательный
  доступ к единственному соединению (см. 1.6).
- **Миграции.** Нумерованные идемпотентные скрипты (`01…04`), применяются
  повторно: `CREATE OR ALTER`.
- **CI/CD, логгеры, метрики.** Один exe на одном ПК: достаточно лога ошибок
  в `bin\Warehouse.log`. Smoke-тест возвращает 0/1 — при появлении CI
  подключается одной строкой.

Если бы это становилось продуктом, первый шаг — вынести FIFO и проведение
документов в отдельный модуль с явными контрактами и покрыть его тестами на
фикстурной базе.

## 6. Известные ограничения

- **Однопользовательский режим** — следствие 1.6.
- **Документ не редактируется** — только обратная операция (классика учёта).
- **Полный отчёт «остатки на дату» без фильтра по товару на ~1M движений
  считается десятки секунд** (см. раздел 3) — на обычных объёмах (тысячи
  движений) мгновенен.
- **`Extended` (double) для денег в Delphi.** В БД всё `DECIMAL(18,2/3)`;
  на пути приложения — double. На суммах тестового масштаба ошибка
  представимости не проявляется; в продукции считали бы в `Currency`/`DECIMAL`
  end-to-end.
- **Интерфейс не локализован**, один оператор, массового импорта нет.
- **Тайм-аут ODBC по умолчанию** — полный отчёт на нагрузочной базе может его
  выбить из GUI; скрипты замеров считают время на стороне сервера, поэтому
  корректны.
